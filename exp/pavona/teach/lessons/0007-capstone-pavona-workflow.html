Lesson 07 · Capstone

A Repeatable Pavona Workflow

Choose a starting point, install a custom recipe, and prove both can generate clean projects.

Today's win

Complete one end-to-end run: select the right built-in or your custom template, keep the custom recipe under version control, invoke it by XDG name, test quiet and interactive paths, and verify the output without risking an existing project.

Part 1: pick the starting point

Use a built-in when it already matches the shape. Use a custom template when you repeatedly make the same personal choices or need a starter shape the built-ins do not provide.

Part 2: make a versioned custom template

Use the personal setup blueprint from Lesson 5. If you have not applied it to a real setup yet, use my-lib-template from Lesson 4. Before installing, check that its root contains config.cue, and that you have classified each file as rendered, verbatim, or a separate template variant.

Set the intended XDG data root first. If you are still in the temporary environment from Lesson 3 and want a lasting install, unset that temporary value or set XDG_DATA_HOME to your chosen persistent data directory.

NAME=my-lib-template
XDG_ROOT="${XDG_DATA_HOME:-$HOME/.local/share}"
TEMPLATE_ROOT="$XDG_ROOT/pavona/templates/$NAME"
mkdir -p "$XDG_ROOT/pavona/templates"
if [ -e "$TEMPLATE_ROOT" ]; then
  echo "Template path already exists; inspect it before reusing" >&2
else
  cp -a "./$NAME" "$TEMPLATE_ROOT"
fi

If you use a different template name, keep the directory name and invocation name aligned, and update name: in config.cue for clarity. The destination must be new; don't copy over a template you already maintain there.

Make the installed recipe itself your maintained source, under Git:

git -C "$TEMPLATE_ROOT" init
git -C "$TEMPLATE_ROOT" status --short

If it is already a Git repository, skip git init. Commit a known-good version when ready. Record the initial git status --short so you can compare it after generation. Keep generated project directories outside $TEMPLATE_ROOT.

Part 3: prove both modes

  1. Quiet run: use a fresh output name; this proves defaults and project_name work without prompts. 
    pavona new "$NAME" capstone-quiet -q
  2. Interactive run: again use a fresh output name; inspect and confirm the pre-filled project name, then change one value if the template offers a meaningful choice. 
    pavona new "$NAME" capstone-interactive
  3. Inspect output and source status: 
    find capstone-quiet -maxdepth 3 -type f | sort
grep '^module ' capstone-quiet/go.mod
grep '^package ' capstone-quiet/lib.go
git -C "$TEMPLATE_ROOT" status --short
    Adapt the file checks to your template. Confirm there is no config.cue or unexpected .tmpl suffix in the generated tree. Rendering should not dirty the template repository.
  4. Change one template file and generate a third project into a fresh output directory. Verify the new project reflects the change and the first project does not.

For a real personal library: run the generated project's formatter and tests from inside its directory (for the Lesson 4 sample, cd capstone-quiet && go test ./...). For another project shape, use that project's normal build/test command.

Acceptance check

You can do this without the lesson open when you can:

  • Choose a built-in that fits—or explain why a custom template is justified.
  • Point to one verbatim file, one rendered file, and each genuine user choice.
  • Install and invoke the template by name from outside its source directory.
  • Run quiet and interactive scaffolds into fresh directories and inspect both.
  • Explain why updating the template does not update old generated projects.
  • Diagnose a missing template, missing required value, render key error, or non-empty output error by layer.
