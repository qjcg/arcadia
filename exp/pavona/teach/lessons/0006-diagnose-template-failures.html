Lesson 06 · Reliability

Diagnose by Layer

Find which stage failed before changing the template at random.

Today's win

You'll introduce one deliberate typo into a throwaway template, recognize the missing-key error, fix it, and recover into a fresh output directory. Then use the same short diagnostic ladder for the other common Pavona failures.

The diagnostic ladder

Read the first useful error, then look at the corresponding layer:

SymptomLayerFirst check
template "x" not foundResolveBuilt-in name → exact directory with config.cue → XDG path. Built-ins win name collisions.
CUE/config errorParseValid CUE syntax and required top-level fields: name, description, variables.
required values missingPrompt / validateIn -q, every variable gets its default. A required field without one stays empty; --name only pre-fills project_name.
Missing map key during renderHydrateCompare every {{.key}} with names in config.cue. Pavona uses missingkey=error for content and paths.
Undefined function in a pathHydrate pathPath rendering has no custom functions; sanitize is only registered for rendered file content.
Output directory exists and is not emptyWrite outputUse a new or empty directory. Pavona doesn't merge or upgrade projects.

Hands-on: make one failure, then recover

Use my-lib-template from Lesson 4. Keep this experiment separate from the working template:

  1. Copy it and add a misspelled key. Choose a fresh test template/output name if these already exist. 
    cp -a my-lib-template my-broken-template
printf '\n// {{.descripton}}\n' >> my-broken-template/lib.go.tmpl
    The template defines project_name, not descripton.
  2. Run the throwaway scaffold: 
    pavona new ./my-broken-template broken-output -q
    It should fail with a template execution error mentioning the missing key. The exact wording depends on Go's template error, but the important fact is that Pavona did not silently replace the typo with blank text.
  3. Repair the source and try a fresh output path. Edit my-broken-template/lib.go.tmpl, changing .descripton to .project_name. Then run: 
    pavona new ./my-broken-template repaired-output -q
grep '^package ' repaired-output/lib.go
    A failed hydration can leave partial files behind. Don't retry into broken-output; Pavona will correctly reject that now-non-empty directory.

Protect real work. The lesson's broken-output is disposable. If a render fails in a real workflow, inspect the directory before deleting or moving it; only clean up when you have confirmed it contains just generated test output. Always retry to a fresh path.

Make the common cases boring

  • Before -q: ensure each required variable has a value source. The CLI name only fills the variable literally named project_name.
  • Before rendering: search *.tmpl files and templated paths for {{.; verify every key is declared.
  • Before a test run: choose a fresh output directory; don't treat Pavona as an update command.
  • After a successful run: inspect the generated tree, check rendered values, and run the generated project's formatter/tests/build.

Retrieval practice

Answer from memory before clicking. One attempt each.

1. A required project_name has no default. What if you use -q without a name?

Quiet mode uses the empty default; required-value validation then stops the run. Supply a name or a default.

2. A .tmpl references an undeclared variable. What happens?

missingkey=error catches the absent key during template rendering.

3. What does Pavona do with a non-empty output directory?

Use a new or empty destination; generated projects are not upgraded in place.

4. A render failed and left files in its test output. How should you retry?

First inspect the partial directory; after confirming it's disposable, retry using a fresh path.
