Lesson 01 · Pavona from the ground up

Anatomy of a Template

One mental model: a template is a directory with a config.cue brain.

Today's win

By the end you will have built a working custom template from scratch — two files — generated a project from it, and be able to predict exactly which files land in the output and what's in them. That prediction skill is the whole foundation for maintaining templates later.

The mental model

pavona new runs a three-stage pipeline (design.md § Architecture):

  1. Resolve — find the template directory: built-in name → path with config.cue → ~/.local/share/pavona/templates/<name>/.
  2. Prompt — parse config.cue and build one form with a field per variable (skip the form with -q: every variable becomes its default).
  3. Hydrate — walk the directory and write the output project.

Everything you need to remember lives in step 3's three file rules:

In the template…lands in the project as…
README.md.tmplREADME.md — rendered via Go text/template, variables filled in
Makefile (no .tmpl)Makefile — copied byte-for-byte
config.cue— (consumed by Pavona, never written)

Variables are the data context. If config.cue declares project_name and greeting, your templates reference them as {{.project_name}} and {{.greeting}}. Nothing more magic than that.

Hands-on: your first template

  1. Create the template directory with a config.cue brain: 
    mkdir -p my-first-template
cat > my-first-template/config.cue <<'EOF'
package template

name:        "my-first-template"
description: "Greets the world from a new project"

variables: {
	// Name of the new project
	project_name: string

	// Greeting message
	greeting?: string | *"Hello, World!"
}
EOF
    Note: project_name has no ? → required. greeting is optional with a default. The doc comment above each field becomes its prompt.
  2. Add one rendered file and one verbatim file: 
    cat > my-first-template/README.md.tmpl <<'EOF'
# {{.project_name}}

{{.greeting}}
EOF
cat > my-first-template/Makefile <<'EOF'
.PHONY: greet
greet:
	@echo "make says hi"
EOF
  3. Generate a project. The positional name sets both the output directory and the project_name variable: 
    pavona new ./my-first-template demo-greeting
    Pavona shows all variables together in one form, sorted alphabetically. project_name is pre-filled with demo-greeting; greeting starts with its default. Confirm the form to accept them, or navigate to change either value.
  4. Verify the prediction: 
    cat demo-greeting/README.md   # rendered: name + greeting filled in
cat demo-greeting/Makefile    # verbatim: exactly what you wrote

Quiet mode gotcha. pavona new ./my-first-template -q skips prompts and uses defaults — but project_name has no default, so it comes out empty and Pavona exits with required values missing. Fix: pass the name positionally (which pre-fills it) or add a default.

Retrieval practice

Answer from memory before clicking. Single attempt — the struggle is the point.

1. Which file never appears in the generated project?

config.cue is consumed by Pavona as the template's definition and is never copied to the output.

2. A template file named hello.txt.tmpl appears in the output as…

Files ending in .tmpl are rendered through Go text/template and written without the .tmpl suffix.

3. How do you mark a config.cue variable optional?

Optional fields use CUE's ? suffix: greeting?: string. (A * marks a default, a different thing.)

4. In -q mode, a required variable with no default causes…

Quiet mode fills every variable with its default; a required variable left empty then fails validation with required values missing and the run aborts.
