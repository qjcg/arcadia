Design Variables That Help

Freeform for open questions. Choices for bounded ones. Defaults for sensible paths.

Today's win

You'll extend your custom template with a license selector, then generate two projects: one where you choose a license interactively, and one where -q selects the default. You will see how a small config.cue design decision changes the user's whole experience.

Choose the right prompt shape

Use when…CUE shapeWhat Pavona shows
Answers are open-ended: name, descriptionfield: stringText input; required unless ?
Answers come from a known, finite setfield: "a" | "b"Select menu; required unless ?
There is a good standard answer*"default"Pre-filled input or pre-selected choice

The field's doc comment becomes its prompt label. Pavona currently puts every variable in one form, sorted alphabetically — not one page per variable. You can navigate between fields and change pre-filled answers before submitting. [Source: Interactive Prompt Flow]

Make a license selector

In Lesson 1 you made my-first-template. Keep using it. A license has a short, known set of valid answers — it is a choice, not freeform text. Add this inside its variables: { ... } block:

	// License identifier for the project
	license?: "MIT" | *"Apache-2.0" | "BSD-3-Clause"

Read the syntax aloud:

  • license? — optional. Pavona won't require an answer; if you render it, an unanswered value is empty.
  • "MIT" | ... | "BSD-3-Clause" — finite choices → select menu.
  • *"Apache-2.0" — pre-selected default. The default must be one of the choices.
  • // License identifier ... — the label shown to the user.

Now add a line to README.md.tmpl, below the greeting:

License: {{.license}}

See both paths

  1. Interactive: choose a different value. 
    pavona new ./my-first-template license-demo
    All three fields appear together, alphabetically. project_name is pre-filled with license-demo (it remains visible); greeting and license start at their defaults. Navigate to License, choose MIT, then submit. Check license-demo/README.md.
  2. Non-interactive: accept all defaults. 
    pavona new ./my-first-template quiet-demo -q
cat quiet-demo/README.md
    This time the README should say Apache-2.0. Quiet mode takes the declared default for each variable; the positional name pre-fills project_name too.

Default must be a valid choice. Pavona selects the default choice when it exists in the list. If the configured default isn't one of the choices, the implementation falls back to the first listed choice. Don't rely on that fallback: keep the default inside the disjunction so the prompt and -q agree.

One design test

For each variable in a template, ask:

  1. Can users reasonably type many different answers? Use a freeform string.
  2. Are valid answers a small, known set? Use a choice so typos and invalid values are impossible.
  3. Can most users safely accept one answer? Give it a default; that is what -q uses.
  4. Must every generated project have a value? Make it required. A required field without a default will fail in -q unless supplied with --name (for project_name) or otherwise given a default.

Retrieval practice

Answer from memory before clicking. One attempt each.

1. What does license: "MIT" | "Apache-2.0" define?

No ? means required; the literal disjunction means select; no * means no default.

2. What if a choice default is not in its choices?

The current implementation falls back to the first listed choice. Still, declare a valid default so interactive and quiet runs are predictable.

3. How does Pavona present multiple variables?

All fields are in one Huh form group, in alphabetical order; users can navigate and edit before submitting.

4. What does pavona new ... --name demo do to project_name?

It sets the variable's default before prompting. The field remains part of the form (the CLI help currently says it skips the prompt, but the implementation still displays it pre-filled).
